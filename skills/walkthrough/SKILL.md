# 작업 워크스루

커밋 범위 하나를 읽고, 그 작업을 **남에게 설명하는 자료**로 바꾼다. 결과물은 사용자가 고른 형식으로 나오고, 마지막 채팅 응답은 그 자체가 발표 브리핑이다 — 사용자가 응답만 보고도 핵심을 간추려 말할 수 있어야 한다.

**입력**: 커밋 범위(없으면 Step 1에서 묻는다), 출력 형식(없으면 Step 2에서 묻는다). 선택: 청중(기본 "같은 코드베이스를 아는 동료 개발자"), 출력 언어(기본 사용자 언어).

**대원칙 — 장면이 단일 진실 원천**: 커밋을 읽어 먼저 **장면** 목록을 만들고, 문서·대본·HTML 투어는 모두 그 장면 목록을 같은 순서·같은 번호로 렌더링한 것이다. 형식 간에 내용이 어긋나면 장면 목록을 고치고 다시 렌더링한다.

## 플로우

```
범위 확정 → 형식 선택 → 커밋 읽기 → 장면 목록 → 렌더링 → 브리핑
```

## Step 1. 범위 확정

인자 해석 규칙. 한국어 "A부터 B까지"는 A를 **포함**하지만 git `A..B`는 A를 제외하므로, 말로 받은 범위는 `A^..B`로 옮긴다.

| 사용자 표현 | git 범위 |
|---|---|
| 단일 SHA | `<sha>^..<sha>` |
| "A부터 B까지" (SHA 두 개를 말로) | `A^..B` |
| `A^..B`, `A..B` 등 git 문법 그대로 | 그대로 |
| "최근 N개" | `HEAD~N..HEAD` |
| 브랜치 / "이 브랜치 전부" | `$(git merge-base <base> HEAD)..HEAD` (base는 main/master/develop 중 존재하는 것, 모호하면 묻는다) |
| PR 번호 | `gh pr view <n> --json baseRefName,headRefName` → 위 브랜치 규칙 |

- 인자가 없으면 `git log --oneline --decorate -20`을 보여주고 AskUserQuestion으로 시작 커밋(포함)과 끝 커밋(기본 HEAD)을 묻는다. 옵션에 "현재 브랜치가 base에서 갈라진 뒤 전부"를 넣는다.
- merge 커밋은 `--no-merges`로 제외한다. 범위 전체 diff는 `git diff <start>^ <end>`(브랜치면 `git diff <base>...HEAD`)로 본다.
- 확정 후 `git log --oneline --reverse --no-merges <range>` 출력을 사용자에게 그대로 보여준다. 범위가 타이핑된 `A..B`에서 왔으면 "A는 제외됨"을 한 줄 덧붙인다.

**완료 기준**: 범위가 SHA 목록으로 확정되고, 그 목록이 사용자에게 보였음.

## Step 2. 형식 선택

인자에 형식이 없으면 AskUserQuestion으로 묻는다 (Step 1 질문과 한 번에 물어도 된다):

- **문서 + 대본 세트** — 읽기 좋은 `.md`(mermaid 포함) + 그 문서를 화면에 띄우고 읽는 대본. 대본의 모든 문단은 문서의 어느 위치인지 큐로 가리킨다.
- **HTML 투어** — 다음 버튼으로 장면을 넘기는 단일 HTML 파일.
- **둘 다**

산출물 위치: 저장소 루트의 `walkthroughs/<YYYYMMDD>-<slug>/`. slug는 작업을 영문 케밥 1~3단어로.

**완료 기준**: 형식과 출력 경로가 확정됨.

## Step 3. 커밋 읽기

diff 요약이 아니라 **왜 이렇게 했는가**를 캐낸다.

- "왜"의 1차 출처는 커밋 메시지 → PR 본문 → 연결된 이슈 순.
- `git show --stat <range>`로 전체를 본 뒤 커밋별 `git show`. 변경된 함수마다 호출 경로를 Grep/Read로 추적해 diff만으로 안 보이는 메커니즘(누가 부르고, 무엇이 달라지는가)을 잡는다.
- 변경 전 코드는 `git show <start>^:<file>`로 확인해 before/after를 정확히 한다.
- 커밋마다 뽑을 것: 배경/문제, 결정과 버린 대안(메시지·주석·PR 논의에 있으면), 변경 전후 동작, 영향 범위, 위험/주의, 검증 방법.

**완료 기준**: 범위의 모든 커밋에 대해 위 여섯 항목을 채웠고(모르면 "출처 없음"으로 표시), 호출 경로를 추적하지 않고 넘어간 함수 변경이 0건. 변경 파일이 30개를 넘으면 장면의 evidence에 오르는 함수만 추적한다.

## Step 4. 장면 목록

**이해 순서**로 배열한다. 커밋 순서가 아니다 — 보통 문제 → 접근 → 핵심 변경 → 부수 변경 → 검증 → 남은 일.

각 장면:

- `id` 순번, `title`, `key` — 청중이 이 장면에서 가져갈 것 **한 문장**
- `evidence` — 짧은 SHA + `파일:라인` 1개 이상
- `visual` — 흐름·구조·상태 변화라서 글보다 그림이 빠를 때만 종류를 적는다 (flowchart / sequence / state / class). 아니면 none.
- `qa` — 예상 질문과 답 0~2개

장면 수는 5~9개. 1번 장면은 항상 "한 줄 요약 + 전체 지도(overview 다이어그램)", 마지막 장면은 항상 "검증과 남은 일".

**완료 기준**: 커밋→장면 매핑 표가 있고 빠진 커밋이 0개, 모든 장면에 evidence가 있음.

## Step 5. 렌더링

장면 목록을 형식으로 옮긴다. 장면 순서·번호·제목은 형식 간에 동일하다.

- 문서 + 대본 세트: `reference/md-script-format.md`를 읽고 그 구조대로 `walkthrough.md`와 `script.md`를 쓴다.
- HTML 투어: `reference/tour-format.md`를 읽고 `reference/tour-template.html`을 `tour.html`로 복사한 뒤 데이터 블록만 채운다. 완성 후 `open tour.html`.

**완료 기준**:

- 문서: 장면 수만큼 `## N.` 섹션이 있고 1번 장면에 mermaid가 있음.
- 대본: 모든 `§N` 큐가 문서에 실재하는 `## N. 제목`과 번호·제목 모두 일치함 (grep으로 대조).
- HTML: `reference/tour-format.md`의 검증 스크립트가 통과하고(유효한 JSON, `scenes.length` = 장면 수) `open`으로 브라우저에 띄웠음.

## Step 6. 브리핑 (채팅 응답)

마지막 응답은 고정 형식. 사용자는 이것만 보고 발표한다.

1. **한 줄 요약** — "이 작업은 〈목적〉을 위해 〈무엇〉을 〈어떻게〉 바꿨다".
2. **핵심 포인트 3~5개** — 발표 순서대로, 각 1~2문장 + 근거 파일 하나.
3. **예상 질문 1~3개**와 한 줄 답.
4. **산출물 경로** — 파일별 한 줄. untracked 상태임을 한 줄로 알린다.
5. **첫 마디** — 발표를 여는 첫 문장. 대본이 있으면 1번 장면의 첫 문장과 같게.

**완료 기준**: 다섯 항목이 모두 있고, 1~3번이 화면 한 장(약 300단어) 안에 들어옴.
